# Задача 2 — HTTP-клиент и разбор ошибки сервера

Этап: 0 — Каркас.
Зависимости: [задача 1](./01-project-scaffold.md) (`VITE_API_BASE_URL`,
`src/api/api-base-url.ts`, тестовый раннер).
Ссылка на ТЗ: [раздел «Этап 0»](../../03-technical-specification.md#этап-0--каркас)
(HTTP-клиент: базовый URL, JSON, разбор ошибки, место для access-токена)
и [раздел 2](../../03-technical-specification.md#2-общие-технические-требования)
(одно место разбора тела ошибки).
Карта контракта: [общие правила](../../02-staff-api.md#1-общие-правила).
Форма тела на сервере:
[`ErrorResponseBody`](../../../../quizbeat-srv/src/errors/global-exception.filter.ts)
в `quizbeat-srv`. Поля, уже перечисленные в карте, здесь не повторяются.

## Зачем

Разбор ошибки и подстановка access-токена нужны каждому следующему
экрану. Их место — до оболочки и до логина: от экранов клиент не зависит,
а этап 1 должен звать уже готовый вызов, а не заводить второй `fetch`
внутри формы. Логин, хранение refresh и поведение `401` в эту задачу не
входят — у них отдельный DoD с живым сервером.

## Границы задачи

| Входит | Не входит |
|---|---|
| Один клиент: база из задачи 1, JSON-вызов, разбор ошибки, заголовок `Authorization`, когда токен уже есть | `POST /auth/staff/login`, refresh, logout, запись в `localStorage` — [этап 1](../../03-technical-specification.md#этап-1--сессия-сотрудника) |
| Нормализация `message` (строка или массив) в одном модуле | Повтор запроса после `401` и общий refresh на пачку параллельных отказов — тот же этап 1, раздел 2 ТЗ |
| Низкоуровневый вызов, который не навязывает JSON телу | Multipart (`file` / `files`) — [этап 5](../../03-technical-specification.md#этап-5--аудио-и-отрезки) и [этап 6](../../03-technical-specification.md#этап-6--изображения-композиции). Здесь только не запереть клиент так, чтобы тот этап переписывал транспорт |
| | Оболочка, тема, роутер — [задача 3](./03-app-shell.md). Экран клиент не импортирует |

## ⚠ Технические нюансы и ограничения

- `message` в теле — строка или массив строк. В массив его превращает
  валидация на сервере. Разбор, который делает `String(message)` или
  берёт только `[0]`, на валидации либо склеивает запятыми через
  приведение массива, либо прячет остальные пункты. Наружу клиент отдаёт
  список строк: одна, если сервер прислал строку.
- Успех без тела — нормальный ответ, не ошибка парсинга. Logout на этапе
  1 отвечает `204` и тела не имеет. `response.json()` на пустом теле
  бросает `SyntaxError`, и вызывающий код примет успех за сбой. Пустое
  тело при статусе 2xx — это `undefined`, не исключение.
- Тело ошибки тоже бывает не JSON: прокси, обрыв, HTML. Тогда у
  исключения остаётся HTTP-статус, а сообщение собирается без падения
  на `JSON.parse`. Статус важнее текста «Unexpected token».
- Сетевой отказ `fetch` (хост недоступен) — не HTTP-ошибка: статуса нет.
  Его нельзя оформлять как `401` и нельзя запускать через ветку refresh,
  когда та появится на этапе 1. Отдельный тип или явный признак «запрос
  не дошёл».
- Access-токен приходит снаружи функцией «дай текущий токен». Клиент сам
  не читает `localStorage` и не разбирает JWT. Пустая строка и `null` —
  заголовка `Authorization` нет. Заголовок собирается здесь и только
  здесь; экраны этапа 1 не конкатенируют `Bearer` сами.
- `credentials: 'include'` не ставить. Сервер отдаёт токены в JSON, не в
  cookie, а CORS бэкенда не включает credentials
  (`enableCors({ origin })` в `quizbeat-srv/src/setup-app.ts`). С этой
  опцией браузер отклонит ответ ещё до разбора тела.
- Склеивать URL через `new URL(path, base)`, если `path` начинается с
  `/`, опасно в тот момент, когда база когда-нибудь получит префикс пути:
  такой `path` отбрасывает путь базы и остаётся только origin. База уже
  нормализована в задаче 1 (без завершающего `/`), путь вызова начинается
  с `/`, соединение — конкатенация.
- Файл `src/api/api-base-url.ts` пишет задача 1. Здесь его импортируют и
  не меняют. `src/main.tsx`, `src/app/**` и `package.json` эта задача не
  трогает — их параллельно может занимать задача 3.

## Объём работы

- Модуль ошибки, один на приложение. Из тела карты получается список
  сообщений для экрана. Поле `details`, если сервер его прислал,
  сохраняется и никуда само не рисуется. Чужое или неразобранное тело не
  теряет статус.
- Клиент с двумя уровнями:
  - низкоуровневый вызов принимает путь, метод и уже готовое тело
    (`BodyInit` или его отсутствие) и не выставляет
    `Content-Type: application/json` сам;
  - JSON-обёртка сериализует объект, ставит `Content-Type` и зовёт
    низкоуровневый вызов.
  Так этап с файлами добавит `FormData`, не развивая второй клиент.
- База — константа из `src/api/api-base-url.ts`. Токен — аргумент
  конструктора или фабрики: `() => string | null`. Заголовок
  `Authorization: Bearer <token>` ставится только при непустом значении.
- Любой статус вне 2xx — отклонение с разобранной ошибкой, включая `401`
  и `429`. Повтора запроса нет.
- Успех с JSON-телом возвращает разобранное значение. Успех с пустым
  телом возвращает `undefined`.
- Тесты на моке `fetch`, без сервера и без jsdom-экрана:
  - `message` строкой и `message` массивом;
  - статус 2xx без тела;
  - не-JSON тело при 4xx/5xx — ошибка со статусом, без исключения парсера;
  - заголовок `Authorization` есть, когда геттер вернул токен, и отсутствует,
    когда геттер вернул `null` или `''`;
  - ответ `401` не приводит ко второму `fetch`.

## Критерии готовности

- Тест: строка в `message` и массив в `message` оба доступны вызывающему
  коду как список строк, ни один элемент массива не отброшен.
- Тест: ответ `204` с пустым телом не бросает ошибку разбора.
- Тест: тело `not-json` при HTTP-ошибке даёт ошибку с этим статусом.
- Тест: `Bearer` выставляется только из непустого токена геттера; при
  `401` уходит ровно один запрос.
- `npm run lint` и `npm run test` проходят. `npm run build` проходит:
  клиент типизируется вместе с константой базы из задачи 1.
