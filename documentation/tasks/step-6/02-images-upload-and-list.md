## Зачем

Без блока на существующей карточке DoD «несколько картинок загружаются»
и превью не закрыть. Задача фиксирует поле `files`, подсказку типов
(без SVG), клиентский лимит 1…10 и показ отказа API до DnD и удаления.
Порядок и удаление сюда не тащить: иначе тест multipart смешается с
полным `imageIds` и диалогом.

## Границы задачи

| Входит | Не входит |
|---|---|
| Блок на `/compositions/:id`: выбор файлов, подсказка jpg / png / webp и ориентир 10 МБ, вызов метода стора (1…10 файлов) | Перетаскивание порядка — [задача 3](./03-images-reorder.md) |
| Начальный список — `images` из ответа `full`, уже полученного [задачей 4 этапа 4](../step-4/04-composition-card.md); превью по `fileUrl` из ответа загрузки / `GET .../images` после мутаций | Удаление с подтверждением — [задача 4](./04-images-delete.md) |
| Показ `message` при `400` / `413` / `415` и при отказе сервера на обход лимита | Собственный первый `GET .../images` на маунте — карточка уже получила список. Заметки — [этап 7](../../03-technical-specification.md#этап-7--заметки-а-знали-ли-вы) |
| | Смена маршрута карточки. Аудио этапа 5 не переписывать |

## ⚠ Технические нюансы и ограничения

- Имя поля — `files`. Клиентская подсказка расширений не заменяет
  проверку по содержимому. SVG не предлагать. Отказ — `message` как
  пришёл. Сверхлимит на этом маршруте — `413` `File too large` (multer,
  не строка валидатора хранилища) — см.
  [README](./README.md#решения-по-открытым-вопросам-этапа).
- `fileUrl` есть сразу; опроса статусов нет (не копировать отрезки).
  Presigned URL не класть в стор навсегда: при битой превью —
  перечитать `GET .../images`.
- После успешного `201` список обновляется ответом мутации или
  повторным `GET` — достаточно одного актуального массива на блоке.
- Блок сажается **после** блоков этапа 5 на том же файле карточки.
  При конфликте слияния с задачами 3–4 — эта задача вливается первой
  после стора, см. [порядок](./README.md#почему-такой-порядок).
- Текст подсказок и ошибок — React-текст, без
  `dangerouslySetInnerHTML`. Загрузка файлов — категория обязательного
  человеческого ревью (поле multipart и обещания про тип/размер), см.
  [README](./README.md).
- Карточка (этап 4) уже открывается одним `GET .../full` и хранит
  `images` в своём состоянии; этот блок читает их оттуда при появлении
  на экране и не делает собственный `GET .../images` на маунте.

## Объём работы

- На карточке композиции — блок «Изображения» ниже блоков этапа 5:
  input файлов (multiple) или эквивалент MUI, русская подсказка
  допустимых типов (jpg, png, webp; без SVG) и ориентира 10 МБ,
  кнопка загрузки.
- Начальное состояние блока — `images` из состояния карточки (ответ
  `full`); пустой массив — пустое состояние списка. Собственный
  `GET .../images` на маунте не вызывается.
- Выбор: клиент не отправляет 0 файлов и отсекает набор >10 до сети
  (или не даёт выбрать больше); отказ сервера при обходе всё равно
  показать.
- Успех `201`: превью по `fileUrl` новых и/или обновлённого списка
  (перечитанного `GET .../images`).
- Отказы API показать на блоке без очистки сессии.
- Тесты:
  - выбор файлов и отправка вызывают стор / `fetch` с полем `files`;
  - набор из 11 файлов из UI/хелпера блока в сеть не уходит (или
    стор отвергает до `fetch` — согласовать с запретом задачи 1);
  - при `201` на экране есть превью по `fileUrl` из ответа;
  - `415` / `413` / `400` с `files is required` показывают `message`;
  - блок не делает вызов `GET .../images` на маунте, если в состоянии
    карточки уже есть массив `images` (в том числе пустой) из `full`;
    не вызывает путь `/full` сам.

## Критерии готовности

- Тесты из объёма работы проходят через `npm run test`.
- `npm run lint` проходит.
- Ручной проход: на карточке можно выбрать jpg/png/webp и увидеть
  либо превью, либо `message` сервера. Полный DoD с порядком и
  удалением — у [приёмки](./05-step6-acceptance.md).
