# Задача 4 — Роль, деактивация и повторная активация

Этап: 2 — Сотрудники.
Зависимости: [задача 2](./02-admins-list.md) (строка списка) и методы
правки и деактивации из [задачи 1](./01-admins-store.md). Метод «забыть
только refresh» — [стор сессии](../step-1/01-session-model.md).
Ссылка на ТЗ: [раздел «Этап 2»](../../03-technical-specification.md#этап-2--сотрудники)
(`PATCH /admins/:id`, `DELETE` как деактивация с телом `200`, access

Карта: строки `PATCH /admins/:id` и `DELETE /admins/:id` в
[сотрудниках](../../02-staff-api.md#3-сотрудники).
Сервис —
[`AdminsService`](../../../../quizbeat-srv/src/admin/admins.service.ts)
(`update` не отзывает refresh, `remove` отзывает), отказ последнего
супер-админа —
[`LAST_SUPER_ADMIN_MESSAGE`](../../../../quizbeat-srv/src/admin/constants.ts).

## Зачем

Деактивация и активация на сервере — разные методы, и их легко свести к
одному `PATCH` с boolean. `update` при `isActive: false` токены не
отзывает: после повторной активации прежний refresh снова принимается.
`remove` помечает токены отозванными, и повторная активация их не
восстанавливает: входить нужно паролем. ТЗ описывает деактивацию как
`DELETE`. Задача опирается на готовую строку из задачи 2: без email и
статуса в подтверждении некого назвать, а смена статуса до ответа
сервера скроет `409` последнего супер-админа.

## Границы задачи

| Входит | Не входит |
|---|---|
| Смена роли через `PATCH` с полем `role` | Создание — [задача 3](./03-create-admin.md) |
| Деактивация через `DELETE`, с подтверждением | `PATCH` с `isActive: false` вместо `DELETE` |
| Повторная активация через `PATCH` с `isActive: true` | Сброс пароля — [задача 5](./05-reset-password.md) |
| `409` последнего супер-админа показывается, строка до ответа сервера не меняется | Подсчёт супер-админов по текущей странице, чтобы спрятать кнопку |
| `DELETE` своей строки забывает refresh и оставляет access | Немедленный logout и переход на логин |

## ⚠ Технические нюансы и ограничения

- Деактивация — `DELETE`. Повторная активация — `PATCH` с телом
  `{ isActive: true }`. В теле это boolean, не строки `true` / `false`:
  строки относятся к query списка, см.
  [задачу 1](./01-admins-store.md) и
  [решения этапа](./README.md#решения-по-открытым-вопросам-этапа).
  У неактивной строки на экране действие «активировать», у активной —
  «деактивировать». По неактивной строке интерфейс `DELETE` не шлёт.
- Текст подтверждения деактивации по-русски говорит три вещи: учётка
  перестанет входить и продлевать сессию; уже выданный access доживёт
  до своего TTL; активировать снова можно. Формулировки «удалить
  навсегда» нет: при фильтре «все» строка из списка не исчезает. Отмена
  подтверждения не вызывает `fetch`.
- `409` с текстом
  `Cannot deactivate or demote the last active SUPER_ADMIN`
  показывается как `message`. Роль и статус на экране остаются такими,
  какими их прислал последний успешный список. Кнопку клиент не прячет
  по числу супер-админов на странице: фильтр и пагинация это число не
  дают восстановить.
- Смена роли шлёт `{ role }` и не забывает refresh: серверный `update`
  токены не отзывает. Роль в шапке и пункт меню по-прежнему берутся из
  access. Понижение собственной роли не записывает ответ `PATCH` в стор
  сессии.
- Если id строки совпал с id сессии, после `200` на `DELETE` вызывается
  метод «забыть только refresh». Access остаётся, logout не вызывается,
  `POST /auth/staff/refresh` не вызывается. Чужой id сессию не меняет.
  Успешный `PATCH` роли этот метод не вызывает.
- После `200` список перечитывается с текущими фильтрами. Ответ
  изменения в таблицу в обход этого запроса не вставляется.
- Экран списка общий с задачами 3 и 5. Эта задача добавляет на строку
  смену роли, деактивацию и активацию. При конфликте слияния она идёт
  после задачи 3 и до задачи 5, см.
  [README](./README.md#почему-такой-порядок).

## Объём работы

- На активной строке: смена роли на другое из двух значений (`ADMIN`
  или `SUPER_ADMIN`) и деактивация с подтверждением. На неактивной —
  активация. Подписи русские.
- Деактивация после подтверждения вызывает `DELETE`. Активация вызывает
  `PATCH` с `{ isActive: true }` и без поля `role`, если роль не
  менялась. Смена роли вызывает `PATCH` с `{ role }` и без `isActive`,
  если активность не менялась.
- `DELETE` по своему id забывает refresh текущей вкладки и оставляет
  оболочку. `DELETE` по чужому id ключ refresh не трогает.
- Тесты на моке `fetch`:
  - подтверждённая деактивация шлёт `DELETE` и не шлёт `PATCH` с
    `isActive: false`; отмена не шлёт ничего;
  - активация шлёт `PATCH` с boolean `true`;
  - `409` с текстом про последнего супер-админа показывает эту строку,
    подпись роли в строке списка не меняется;
  - `DELETE` по своему id вызывает «забыть refresh», access на месте,
    запроса `/auth/staff/refresh` нет;
  - успешный `PATCH` роли метод «забыть refresh» не вызывает.

- Тесты из объёма работы проходят через `npm run test`.
- `npm run lint` и `npm run build` проходят.
