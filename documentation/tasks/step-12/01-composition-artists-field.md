# Задача 1 — Поле «Исполнители» в композициях

Этап: 12 — Исполнители вместо автора.
Зависимости: серверный этап 17,
[задача 2](../../../../quizbeat-srv/documentation/tasks/step-17/02-staff-artists-and-compositions.md)
(`/artists`, `artistIds`, `artists`); [HTTP-клиент](../step-0/02-http-client.md);
композиции — [этап 4](../step-4/README.md).
Ссылка на ТЗ: [раздел «Этап 12»](../../03-technical-specification.md#этап-12--исполнители-вместо-автора).
Карта: разделы «Композиции» и «Исполнители» в
[staff-api.md](https://github.com/evilice/quizbeat-docs/blob/main/api/staff-api.md)
(появляются в серверной задаче 2). Поля запроса и ответа здесь не
повторяются.

## Зачем

Поле «Автор» стоит в нескольких местах — создание, правка, список, карточка и
диалог удаления; заменять его по частям значит держать клиент в промежуточном
состоянии, которое сервер не принимает. Поэтому одна задача: стор
исполнителей и все места композиции переключаются вместе.

## Границы задачи

| Входит | Не входит |
|---|---|
| Стор `artists`: `list({ search })`, `create({ name })` | Страница справочника, переименование и удаление — [задача 2](./02-artists-page.md) |
| Компонент «Исполнители»: `Autocomplete multiple`, поиск на сервере, «создать», порядок стрелками | Изменение сервера |
| Создание и правка композиции с `artistIds` | Фильтр списка по исполнителю |
| Колонка «Исполнители» в списке, заголовок и диалог удаления, поиск списка | Разбор составных значений вроде «A, B» на нескольких исполнителей |
| Единая функция подписи исполнителей | Картинки, аудио, видео, заметки |

## ⚠ Технические нюансы и ограничения

- **`artistIds` — зеркало `tagIds`.** Опущен при создании, если не выбрано
  ни одного. В правке уходит **полный упорядоченный набор** только если
  пользователь его менял (как `tagsTouched` у тегов); снять всех —
  `artistIds: []`, а не отсутствие поля. Проверить, как это сделано для тегов
  в `use-edit-composition.ts`, и сделать так же, не придумывать второй
  признак «изменено».
- **Порядок значим и сохраняется.** Массив `artistIds` — в порядке чипов;
  ответ сервера (`artists`) тоже упорядочен; не сортировать на клиенте.
- **Поиск только на сервере и с задержкой.** `GET /artists?search=` с
  ограничением `limit` (20); запрос уходит после паузы ввода (debounce), с
  отменой устаревшего — иначе ответ на «Em» перетрёт ответ на «Emi».
  Короткого таймаута нет.
- **Опции в `Autocomplete` — по `id`,** а не по имени: уже выбранные
  исполнители берутся из `composition.artists` (их может не быть в текущей
  выдаче поиска). Сравнение `isOptionEqualToValue` по `id`.
- **Создание «на лету».** Пункт «Создать «Имя»» показывается, если среди
  результатов нет совпадения имени без учёта регистра. `POST /artists` может
  вернуть `409` (гонка или другой регистр, пока шёл поиск) — тогда клиент
  повторяет поиск по этому имени и выбирает найденного, а не показывает ошибку.
- **Имя — `trim`, пустое не создаётся.** Сообщение об ошибке показывается один
  раз, в самом диалоге (как у остальных ошибок композиций).
- **Заголовок карточки получает исполнителей из `location.state`.** Сейчас
  `use-composition-card.ts` передаёт `author` через состояние навигации
  (`locationState?.author`) до загрузки `GET .../full`; перенести на подпись
  из `artists`, иначе заголовок пропадёт до загрузки.
- **Пустой список — «—»,** а не пустая ячейка и не слово «нет».
- **Файлы, которые трогает и [задача 2](./02-artists-page.md):**
  `root-store.ts`, `src/app/routes.tsx`, `PagesMenu.tsx`. Эта задача
  только регистрирует стор в `root-store.ts`; маршрут и меню добавляет
  задача 2.
- Тесты и хелперы (`compositions-test-helpers.tsx`, `CreateComposition.test.tsx`,
  `CompositionsList.test.tsx`, `CompositionCard.test.tsx`,
  `compositions-store.test.ts`, `App.test.tsx` и др.) строят композиции с
  `author` — обновить, иначе `tsc -b` падает.

## План реализации

1. **Разведка (правило 1).** Прочитать `TagsStore`, `use-tag-options.ts`,
   `use-edit-composition.ts` (как ведёт себя `tagsTouched`), `CompositionEditForm`,
   `CreateCompositionDialog`, `use-composition-card.ts` (состояние навигации).
   Прочитать разделы `staff-api.md` и DTO сервера: если форма ответа
   разошлась с этой задачей, верен код сервера (CLAUDE.md проекта).
2. **Тесты сначала (на моке `fetch`).** Стор: `list` шлёт `search` и `limit`,
   `create` шлёт `{ name }`. Поле: ввод шлёт запрос после паузы, устаревший
   ответ игнорируется; выбор нескольких сохраняет порядок; «Создать»
   вызывает `POST` и выбирает результат; `409` → повторный поиск и выбор
   найденного; выбранные чипы не пропадают при смене строки поиска. Создание:
   без исполнителей — тело без `artistIds`, публикация допустима; с двумя —
   `artistIds` в порядке выбора. Правка: `[]` уходит при снятии всех, без
   изменения поле не уходит. Список и диалог показывают подпись.
3. **Стор `artists`** (`makeAutoObservable`, как `TagsStore`).
4. **Функция подписи** с тестом (несколько имён, пусто → «—»).
5. **Поле «Исполнители»** и подключение к форме создания и правки.
6. **Список, карточка, диалог удаления, фильтры** — подпись; удалить `author`
   из типов и тел запросов.
7. **Регистрация стора, обновление тестов, документация;** `npm run test`,
   `lint`, `build`; `/code-review` (правило 7) и Impact; без подтверждения
   не коммитить.

## Критерии готовности

- `npm run test`, `npm run lint`, `npm run build` проходят; в `src` нет
  поля `author` у композиции (`grep -rn "author" src` — только
  `Authorization`/`authorization`).
- Тесты на моке: создание без исполнителей отправляет тело без `artistIds`;
  порядок выбора совпадает с порядком `artistIds`; правка отправляет `[]` при
  снятии и ничего — без изменений; `409` при создании исполнителя
  разбирается без ошибки на экране; устаревший ответ поиска не перетирает
  свежий.
- Подпись: несколько имён через запятую, пусто — «—» в списке, карточке,
  диалоге удаления.
- Ручной проход на живом сервере — в [задаче 3](./03-step12-acceptance.md).
