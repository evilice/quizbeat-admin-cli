# Техническое задание — клиент админки QuizBeat

Связанные документы: [01-project-overview.md](./01-project-overview.md),
[02-staff-api.md](./02-staff-api.md).

Сервер уже реализован. Этапы ниже — порядок поставки **этого** клиента.
Их номера не продолжают и не повторяют этапы `quizbeat-srv`.

Порядок выбран так, чтобы в приложение можно было войти и проверять его
руками как можно раньше. После этапа 1 есть сессия. После этапа 2
супер-админ заводит вторую учётку и дальше смотрит каждый экран контента
под обеими ролями. Контент идёт следом: теги, композиции — карточка сразу
открывается одним запросом `GET /full`, второго способа её загрузки клиент
не заводит, — затем поверх неё аудио и отрезки, картинки, заметки.
Заключительный этап сводит правило обновления блоков после их мутаций.

Каждый этап вызывает только то, что описано в соответствующем разделе
карты API. Поля, которых нет в карте, берутся из контроллера сервера, и
карта дополняется в том же изменении.

## 1. Технологический стек

- Vite, React, TypeScript.
- MobX и mobx-react-lite.
- MUI (тема, локаль интерфейса `ruRU`).
- react-router.
- Vitest и Testing Library.
- oxlint и Prettier.

Dev-сервер — порт **5173** (`http://localhost:5173`). Это значение
`CORS_ORIGIN_ADMIN` в `.env` бэкенда. Базовый URL API — переменная
`VITE_API_BASE_URL`, по умолчанию `http://localhost:3000`.

Браузерные e2e (Playwright и аналоги) в стек заранее не входят. Задача
может добавить их отдельно, если ручной проход перестаёт быть достаточным
критерием.

## 2. Общие технические требования

Поведение HTTP — по [02-staff-api.md](./02-staff-api.md), раздел «Общие
правила». На клиенте из этого следует:

- Один HTTP-клиент на приложение. Заголовок `Authorization: Bearer` ставит
  он, экраны не собирают его сами.
- Тело ошибки сервера разбирается в одном месте. Пользователь видит
  `message`, не «что-то пошло не так» без содержимого, когда сервер его
  прислал.
- `401` на защищённом запросе: одна попытка `POST /auth/staff/refresh`,
  повтор исходного запроса с новой парой. Неудачный refresh или повторный
  `401` — выход из сессии и экран логина. Параллельные `401` делят один
  refresh.
- Access-токен хранится в памяти. Refresh — в `localStorage`, чтобы сессия
  переживала перезагрузку (сервер отдаёт токены в JSON, не в cookie).
  Почта в шапке — та, что введена на логине и сохранена рядом с refresh:
  в access-токене email нет, `GET /admins/me` нет.
- Скрытие экранов по роли — только навигация. Запрос всё равно уходит с
  токеном, отказ `403` показывается как отказ, а не как пустой экран.
- Списки с пагинацией: поиск и фильтры с первого экрана списка, не второй
  итерацией.
- Presigned-ссылки не сохраняются как постоянные. После истечения TTL
  клиент запрашивает карточку или URL заново.
- Текст с сервера (названия, авторы, переводы тегов и заметок) рендерится
  как текст. `dangerouslySetInnerHTML` для этих полей не используется.
- Документация и коммиты — на русском, идентификаторы в коде — на
  английском.

## 3. Этапы разработки

### Этап 0 — Каркас

- Проект Vite + React + TypeScript, скрипты `dev`, `build`, `lint`, `test`,
  `format`.
- Подключены MobX, MUI, react-router. Тема и русская локаль MUI.
- Оболочка: каркас страницы без рабочих экранов, маршрут-заглушка.
- Переменная `VITE_API_BASE_URL`.
- HTTP-клиент: базовый URL, JSON, разбор ошибки из раздела 2, место для
  подстановки access-токена. Сам логин — этап 1.
- Порт dev-сервера зафиксирован на 5173.

**DoD:** `npm run dev` открывает оболочку на `http://localhost:5173`;
`npm run lint`, `npm run test` и `npm run build` завершаются без ошибок.
Тест проверяет, что оболочка монтируется, а клиент умеет разобрать тело
ошибки сервера (и строку, и массив в `message`).

### Этап 1 — Сессия сотрудника

Карта: [сессия](./02-staff-api.md#2-сессия).

- Экран логина: email и пароль, `POST /auth/staff/login`.
- После входа — оболочка с выходом. `POST /auth/staff/logout` с текущим
  refresh, затем локальная сессия стирается. Ответ logout — `204` без тела.
- Восстановление сессии при загрузке через refresh, если refresh ещё есть.
- Поведение `401` из раздела 2.
- `429` на логине показывается как отказ по лимиту попыток, без
  автоматического повтора.
- Роль и id читаются из access-токена и доступны оболочке. Пункт меню
  сотрудников виден только `SUPER_ADMIN` (сам раздел — этап 2).
- Смена своего пароля: `PATCH /admins/me/password` (текущий и новый, новый
  не короче 8 символов). Ответ — `204`. Доступна любой роли. Чужой сброс
  пароля сюда не входит.

**DoD:** сотрудник входит учёткой, которая есть на сервере (локально это
сид `SUPER_ADMIN` из env бэкенда), после перезагрузки остаётся в сессии,
выход требует нового логина. Неверный пароль показывает сообщение сервера.
Тест покрывает ротацию: один refresh на пачку параллельных `401`, старый
refresh после успеха больше не используется. Проверяется в браузере против
запущенного `quizbeat-srv`, не только моком.

### Этап 2 — Сотрудники

Карта: [сотрудники](./02-staff-api.md#3-сотрудники).

Только `SUPER_ADMIN`. `ADMIN` пункт не видит; прямой заход на маршрут
получает `403` с сервера и показывает отказ, без попытки нарисовать список.
Сразу после сессии, до контента: так можно завести учётку `ADMIN` и дальше
проверять экраны двумя ролями.

- Список `GET /admins`: поиск по email, фильтр роли, фильтр `isActive`
  (в query строки `true`/`false`). По умолчанию сервер отдаёт и
  деактивированных — список это не прячет молча, статус виден.
- Создание `POST /admins`: email, пароль (не короче 8), роль.
- Смена роли и активности `PATCH /admins/:id` (`role`, `isActive`).
  Повторная активация — `isActive: true`, это не отдельный эндпоинт.
- Сброс пароля `PATCH /admins/:id/password` (`204`). Тело — только
  `newPassword`, без текущего пароля цели.
- Деактивация `DELETE /admins/:id` — не удаление строки и не `204`: ответ
  `200` с сотрудником, у которого `isActive: false`, refresh отозваны.
  Уже выданный access может жить до своего TTL; интерфейс не обещает
  мгновенный обрыв чужой сессии.

Смена своего пароля сделана на этапе 1 и здесь не дублируется.

**DoD:** супер-админ создаёт сотрудника, входит под ним, меняет роль,
деактивирует и активирует снова, сбрасывает пароль. Под `ADMIN` раздела
нет, а прямой URL показывает отказ. Проверяется ручным проходом двумя
учётками и тестом видимости пункта меню по роли.

### Этап 3 — Справочник тегов

Карта: [теги](./02-staff-api.md#4-теги).

- Список `GET /tags` с поиском по названию и пагинацией.
- Создание и правка: код и ровно два перевода, `ru` и `en`, оба
  обязательны, поле перевода — `name`. `POST /tags`, `PATCH /tags/:id`.
- Удаление `DELETE /tags/:id` — жёсткое, `204`, с подтверждением.
  Композиции этот тег теряют, сами не удаляются. Восстановления нет.

**DoD:** можно завести тег с обоими названиями, найти его поиском, поменять
название, удалить. Запрос без одного перевода не уходит. Проверяется тестом
формы и ручным проходом против сервера.

### Этап 4 — Композиции

Карта: [композиции](./02-staff-api.md#5-композиции). Аудио, отрезки,
картинки и заметки на этом этапе не делаются — экраны для них появятся на
этапах 5–7. Карточка при этом с самого начала открывается тем же
запросом, каким будет пользоваться весь дальнейший план:
`GET /compositions/:id/full`. Отдельного `GET /compositions/:id` на
сервере нет, и второго, временного способа открыть карточку клиент не
заводит — блоки будущих этапов позже читают поля этого же ответа
(`clips`, `images`, `notes`, `originalAudioUrl`, `originalAudioDurationSec`),
которые до появления соответствующего экрана просто не отрисовываются.

- Список `GET /compositions`: поиск по названию и автору, фильтр статуса
  `DRAFT`/`PUBLISHED`, фильтр тегов. Несколько тегов уходят одним
  параметром `tagIds` через запятую; сервер трактует их как «хотя бы один»
  (OR).
- Создание: название, автор, необязательный статус (если не передан, сервер
  ставит `DRAFT`), необязательный набор тегов. `POST /compositions`.
- Карточка: открывается запросом `GET /compositions/:id/full` (прямой
  заход, переход со списка, перезагрузка — один и тот же способ); правка
  названия, автора, статуса и набора тегов — `PATCH /compositions/:id`.
  Поле `tagIds`, если уходит, заменяет набор целиком, а не дополняет его.
- Удаление `DELETE /compositions/:id` — мягкое, ответ `200` с `deletedAt`,
  с подтверждением. Композиция пропадает из списка. Вернуть её из
  интерфейса нельзя: отдельного восстановления на сервере нет.

**DoD:** черновик создаётся, находится фильтрами, публикуется сменой
статуса, после удаления не виден в списке. Снятие последнего тега
отправляет пустой `tagIds`, а не отсутствие поля. Карточка при открытии,
прямом заходе и перезагрузке делает ровно один запрос `GET .../full` — это
видно по сети в браузере. Проверяется тестом сборки запроса и ручным
проходом против сервера.

### Этап 5 — Аудио и отрезки

Карта: [аудио и отрезки](./02-staff-api.md#6-аудио-и-отрезки).

- Загрузка исходного трека `POST /compositions/:id/audio`, поле `file`.
  Клиент подсказывает допустимые расширения (mp3, wav, flac) и ориентир
  200 МБ. Отказ сервера (тип, размер, нет файла) показывается как ошибка
  API.
- Волновая форма по временной ссылке на оригинал: при открытии карточки —
  поле `originalAudioUrl` полной карточки (её уже читает карточка этапа 4);
  после загрузки нового трека или при протухшей ссылке — отдельный
  `GET /compositions/:id/audio`. Длительность для разметки —
  `originalAudioDurationSec`: при открытии карточки — из полной карточки,
  сразу после загрузки — из тела `201`.
- Разметка точек: старт в секундах, длительность только из набора
  1, 2, 3, 5, 8, 13, 21, сложность `EASY` / `MEDIUM` / `HARD`. Клиент не
  даёт поставить точку, которая вылезает за длительность оригинала; если
  сервер всё равно отклонил — показывается его ошибка.
- Отправка списка `POST /compositions/:id/clips` телом `{ points: [...] }`.
- Список отрезков. Пока есть `PENDING` или `PROCESSING`, клиент опрашивает
  `GET /compositions/:id/clips`. У `DONE` появляется `fileUrl` и его можно
  прослушать. У `FAILED` — явное состояние, не вечная загрузка.
- Удаление отрезка `DELETE .../clips/:clipId` (`204`) и перегенерация
  `POST .../clips/:clipId/regenerate`.

**DoD:** на композиции с загруженным треком можно отметить точки, увидеть
переход статусов до `DONE` или `FAILED`, прослушать готовый отрезок,
удалить его и запустить перегенерацию. Проверяется ручным проходом против
сервера с реальным файлом (нарезка на сервере асинхронная). Тест покрывает
сборку `points` и то, что опрос останавливается, когда незавершённых
статусов не осталось.

### Этап 6 — Изображения композиции

Карта: [картинки](./02-staff-api.md#7-картинки).

- Загрузка `POST /compositions/:id/images`, поле `files`, до 10 файлов за
  раз. Подсказка: jpg, png, webp; SVG не предлагать. Ориентир размера —
  10 МБ на файл.
- Список с превью по `fileUrl`.
- Порядок: `PATCH /compositions/:id/images/order` телом `{ imageIds }` —
  полный список id в новом порядке, не разница. Пустой набор не отправляется.
- Удаление `DELETE /compositions/:id/images/:imageId` (`204`).

**DoD:** несколько картинок загружаются, порядок после перетаскивания
совпадает с повторным чтением списка, удаление убирает карточку.
Проверяется ручным проходом и тестом, что в `imageIds` уходит полный
текущий набор.

### Этап 7 — Заметки «А знали ли Вы?»

Карта: [заметки](./02-staff-api.md#8-заметки).

- Создание и правка: оба перевода `ru` и `en` обязательны, поле перевода —
  `text`. `POST /compositions/:id/notes`, `PATCH .../notes/:noteId`.
  Отдельного `GET` одной заметки на сервере нет — правка идёт из списка.
- Порядок: `PATCH .../notes/order` телом `{ noteIds }` — полный список, тот
  же принцип, что у картинок.
- Удаление `DELETE .../notes/:noteId` (`204`).

**DoD:** заметка с обоими текстами создаётся, меняет порядок, правится и
удаляется. Запрос с одним переводом не уходит. Проверяется тестом формы и
ручным проходом.

### Этап 8 — Сборка карточки композиции

Карта: [композиции](./02-staff-api.md#5-композиции), метод
`GET /compositions/:id/full` (используется с этапа 4, здесь не вводится
заново).

К этому моменту карточка уже открывается одним `GET /full` (этап 4), а
блоки аудио и отрезков, картинок и заметок добавлены этапами 5–7. Этап
фиксирует последнее общее правило: после мутации любого блока (загрузка,
удаление, порядок, нарезка) экран показывает актуальное состояние — либо
обновляет затронутый блок ответом мутации, либо перечитывает список этого
блока своим `GET`. Смешивать устаревший `fileUrl` из первой загрузки с
новым списком нельзя. Новой функциональности, нового маршрута и новых
полей форм на этом этапе нет.

**DoD:** после мутации любого блока (загрузка трека, отправка точек,
удаление, смена порядка, перегенерация) на экране не остаётся устаревших
данных — проверяется тестом на моке для каждой мутации и ручным проходом
на живом сервере. Открытие карточки одним `GET /full`, пустые состояния
блоков и `404` уже проверены на этапах 4–7 и здесь не переповторяются как
новая функциональность.

## 4. Вне текущего плана

- Игровой клиент, `/game/tracks`, регистрация и логин игрока.
- Игровая логика, очки, прогресс, лидерборды.
- Модерация контента, присланного игроками, и тарификация.
- Язык оболочки кроме русского.
- Восстановление удалённой композиции — на сервере такого действия нет.

## 5. Открытые вопросы / принятые по умолчанию решения

Решения приняты при подготовке ТЗ, чтобы не блокировать старт. Их можно
поменять до соответствующего этапа; тогда правится этот раздел и обзор.

1. **Язык оболочки — русский.** Поля контента всё равно двуязычные, потому
   что так требует API. Отдельной локализации интерфейса нет.
2. **Refresh в `localStorage`, access в памяти.** Сервер не ставит cookie.
   Цена — refresh доступен скрипту страницы. HttpOnly-cookie потребовала бы
   изменения бэкенда и в этот план не входит.
3. **Email сессии хранится на клиенте рядом с refresh.** В JWT его нет,
   отдельного `GET /admins/me` на сервере нет.
4. **HTTP-клиент пишется вручную и сверяется с картой и DTO сервера**, а не
   генерируется из OpenAPI на каждой сборке. OpenAPI остаётся справочником
   (`/docs` в development). Генератор можно ввести отдельным решением, если
   ручная сверка начнёт расходиться с сервером.
5. **Библиотека волновой формы выбирается на этапе 5** по тайпингам
   установленной версии. До этого этапа в зависимости она не добавляется.
6. **Линт — oxlint, тесты — Vitest**, как на бэкенде, чтобы не держать
   второй стек инструментов без причины.
7. **Имя репозитория не переименовывается.** В документации продукт
   называется клиентом админки.
