Этап: 0 — Каркас.
Зависимости: нет — первая задача этапа.

## Зачем

Всё остальное на этапе собирается и проверяется уже отсюда: без
`package.json`, фиксированного порта и объявленной переменной API задачи
[2](./02-http-client.md) и [3](./03-app-shell.md) некуда класть код.
Задача специально не включает ни оболочку, ни разбор ошибок — иначе две
следующие задачи правят один и тот же вход приложения и не могут идти
параллельно.

## Границы задачи

| Входит | Не входит |
|---|---|

| Порт dev-сервера 5173 с отказом занять другой | HTTP-клиент, разбор тела ошибки, подстановка access-токена — [задача 2](./02-http-client.md) |

| Пустой вход `src/main.tsx`, который задача 3 заменит | Playwright и другие e2e |

## ⚠ Технические нюансы и ограничения

- В клиентский бандл Vite кладёт только переменные с префиксом `VITE_`.
  `API_BASE_URL` без префикса в коде будет `undefined`, дефолт подставится
  молча, и запросы уйдут на `localhost:3000`, даже если в окружении задано
  другое имя. Читать нужно выражение `import.meta.env.VITE_API_BASE_URL`
  целиком: при деструктуризации `import.meta.env` подстановка Vite не
  срабатывает.
- Порт задаётся как `server.port: 5173` и `server.strictPort: true`. Без
  `strictPort` занятый 5173 превращается в 5174, страница открывается, а
  браузер режет ответы API: в `CORS_ORIGIN_ADMIN` бэкенда записан именно
  `http://localhost:5173`.
- Шаблон Vite для React+TS на актуальном мажоре может включить
  `verbatimModuleSyntax`. Тогда значение и тип импортируются разным
  синтаксисом (`import type`), иначе `tsc` в `npm run build` падает на
  файлах, которые в редакторе выглядят нормально. Не выключать флаг «чтобы
  собралось» — писать импорты так, как требует включённый режим.
- Окружение oxlint на бэкенде — `node`. Здесь копировать его нельзя:
  клиенту нужен `browser`, иначе обращение к DOM в задаче 3 станет
  ошибкой линта. Команда линта — `oxlint --type-aware`, как в
  `quizbeat-srv`, вместе с пакетом, который этот режим требует
  (`oxlint-tsgolint` на бэкенде). Правила, уже принятые там
  (`no-explicit-any` как warn, `no-floating-promises` как error), имеет
  смысл взять теми же: второй набор правил без причины не заводится.
- Prettier на бэкенде — `singleQuote: true`, `trailingComma: all`
  (файл `.prettierrc`). Те же два поля здесь, чтобы дифф между
  репозиториями не шумел из-за кавычек.
- Тестовый раннер не включает globals. Тесты импортируют `describe` /
  `it` / `expect` из `vitest`. Иначе oxlint и TypeScript не видят
  глобальные имена, а «починить» это можно только вторым, расходящимся
  конфигом.
- Конфиг тестов — в одном месте: либо поле `test` в `vite.config.ts`
  (через `defineConfig` из `vitest/config`), либо отдельный
  `vitest.config.ts`. Оба сразу — типичный способ получить jsdom в одном
  и `environment: 'node'` в другом. Для задачи 3 нужен `jsdom`; пакет
  `jsdom` ставится уже здесь, вместе с Testing Library, чтобы задача 3
  не меняла инфраструктуру тестов.
- `src/main.tsx` заводит эта задача, а содержимое экрана заменяет
  [задача 3](./03-app-shell.md). Параллельно с задачей 3 этот файл больше
  не правится. `package.json` после этой задачи меняет только задача 3
  (зависимости MUI, MobX, react-router). Задача 2 зависимостей не
  добавляет.

## Объём работы

- Каркас приложения по официальному шаблону Vite `react-ts` того мажора,
  который ставится в момент реализации. Демо-счётчик шаблона удалить.
  Точку входа оставить пустой: рендер одного текстового узла без MUI,
  достаточного, чтобы `npm run build` собрал бандл. Задача 3 этот рендер
  заменит.
- Скрипты: `dev`, `build`, `lint` (`oxlint --type-aware`), `test`
  (`vitest run`), `format` (Prettier по `src/**/*.{ts,tsx}`).
- `vite.config.ts`: `server.port` 5173, `server.strictPort` true,
  плагин React.
- TypeScript strict. Типы Vite-окружения подключены (`vite/client`),
  чтобы `import.meta.env` типизировался.
- `.gitignore`: `node_modules`, `dist`, `.env`. Файл `.env.example` в git
  остаётся.
- Чтение базового URL — чистая функция в `src/api/api-base-url.ts` и
  константа, которую из неё собирает приложение. Функцию не прятать внутрь
  будущего HTTP-клиента: её тестирует эта задача, клиент в задаче 2 её
  импортирует и файл не переписывает.

| Имя | Тип | Обязательна | Дефолт | Назначение |
|---|---|---|---|---|
| `VITE_API_BASE_URL` | строка, абсолютный URL без завершающего `/` | нет | `http://localhost:3000` | База staff-API. Пустая строка и пробелы считаются «не задано» и дают дефолт. Завершающий `/` снимается |

- Тест на `resolveApiBaseUrl`: не задано, пустая строка, значение с
  завершающим `/`, обычный URL. Тест передаёт строку аргументом и не
  читает `.env` машины: Vitest подхватывает локальный `.env`, и проверка
  через `import.meta.env` начнёт зависеть от того, что лежит у
  разработчика.

## Критерии готовности

- `npm run lint`, `npm run test` и `npm run build` завершаются без ошибок.
  В тесте есть случаи дефолта, пустой строки и срезанного завершающего
  `/` у `VITE_API_BASE_URL`.
- В `vite.config.ts` порт dev-сервера — 5173 и включён `strictPort`.
  Проверяется чтением конфига; живой прогон `npm run dev` — в
  [задаче 4](./04-step0-acceptance.md), чтобы не занимать порт на каждой
  промежуточной задаче.
- `.env.example` содержит `VITE_API_BASE_URL=http://localhost:3000`.
  Проверяется чтением файла.
- В дереве нет темы MUI, роутера и разбора тела ошибки. Проверяется
  составом `src/` после задачи.
