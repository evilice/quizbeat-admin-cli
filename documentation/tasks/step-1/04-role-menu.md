# Задача 4 — Роль в оболочке и пункт меню сотрудников

Этап: 1 — Сессия сотрудника.
Зависимости: [задача 3](./03-login-logout.md) (оболочка после входа,
шапка, маршруты). Роль уже лежит в сторе с
[задачи 1](./01-session-model.md).
Ссылка на ТЗ: [раздел «Этап 1»](../../03-technical-specification.md#этап-1--сессия-сотрудника)
(роль и id доступны оболочке; пункт сотрудников виден только
`SUPER_ADMIN`; сам раздел — этап 2).

## Зачем

Пункт меню — единственная развилка ролей этого этапа, и её закрывают
тестом до того, как этап 2 повесит на тот же пункт список. Откладывать
пункт «на потом, когда появится экран» значит проверять видимость уже
поверх запроса `GET /admins`, хотя ТЗ разделяет эти два шага. Id в
оболочке нужен тем же местом: шапка уже показывает email, роль без
читаемого id на экране нигде не закреплена, и этап 2 начнёт читать его
из JWT заново.

## Границы задачи

| Входит | Не входит |
|---|---|
| Пункт «Сотрудники» в навигации оболочки при `role === 'SUPER_ADMIN'` | `GET /admins`, создание, деактивация, чужой сброс пароля — [этап 2](../../03-technical-specification.md#этап-2--сотрудники) |
| Маршрут-заглушка `/admins` без запроса к API | Подмена прямого захода `ADMIN` самодельным `403`. Отказа сервера на этой заглушке нет; его показывает этап 2, когда маршрут начнёт звать API |
| Id текущего сотрудника доступен оболочке из стора | Смена своего пароля и ссылка на неё — [задача 5](./05-change-own-password.md) |

## ⚠ Технические нюансы и ограничения

- Видимость пункта — строгое равенство роли строке `SUPER_ADMIN`. Роль
  `ADMIN`, пустая роль и любая другая строка пункт не рисуют. Скрытие
  пункта не заменяет серверный `403`: эта задача просто не шлёт запрос,
  который серверу было бы за что отвергать.
- Заглушка `/admins` — тот путь, который этап 2 заменит списком, а не
  временное имя вроде `/staff-later`. Смена пути между этапами сломает
  уже привычный адрес и тест «пункт ведёт сюда».
- Прямой заход на `/admins` под `ADMIN` в этом этапе показывает ту же
  заглушку. Рисовать экран «доступ запрещён» из клиента нельзя: человек
  примет его за ответ сервера, а этап 2 будет вынужден отличать
  самодельный отказ от настоящего `403`.
- Оболочку и таблицу маршрутов уже правит задача 3, параллельно их может
  править задача 5. Эта задача добавляет пункт навигации и маршрут
  заглушки. Ссылку «Сменить пароль» она не вставляет — её место в шапке
  у задачи 5. При конфликте слияния сначала эта задача, потом задача 5,
  см. [README](./README.md#почему-такой-порядок).
- Подпись пункта — текст компонента, не HTML из строки. Роль на экран
  для отладки сырым JWT не выводится.

## Объём работы

- В оболочке с сессией пункт «Сотрудники» виден только супер-админу и
  ведёт на `/admins`.
- `/admins` при любой роли с сессией: русская пометка, что раздел
  сотрудников появится на следующем этапе. `fetch` при открытии нет.
  Без сессии этот путь по-прежнему логин (так устроены маршруты задачи 3).
- Id сотрудника читается оболочкой из стора (то же поле, что разобрала
  задача 1). На заглушке его можно не показывать; запрещено заводить
  второй разбор JWT в компоненте меню.
- Тест Testing Library на двух access, собранных как три сегмента
  base64url без настоящей подписи (клиент её не проверяет):
  - `SUPER_ADMIN` видит пункт «Сотрудники», переход показывает текст
    заглушки;
  - `ADMIN` пункт не видит;
  - открытие `/admins` в обоих случаях не вызывает `fetch`;
  - id в оболочке — тот же `sub`, что в payload. Читается через стор,
    которым пользуется оболочка, а не вторым разбором токена в тесте.

## Критерии готовности

- Тест из объёма работы проходит через `npm run test`: обе роли, отсутствие
  `fetch` на заглушке, id оболочки равен `sub` токена.
- `npm run lint` и `npm run build` проходят: маршрут `/admins` в сборке.
- Поиск по коду заглушки не находит `/admins` как URL запроса (вхождение
  в таблицу маршрутов — ожидаемо). Проверяется чтением компонента
  заглушки: импорта HTTP-клиента нет.
