## Зачем

Список, создание и действия в строке должны вызывать один модуль. Если
каждый экран соберёт query сам, условие `if (isActive)` выкинет фильтр
«неактивные»: `false` в нём ложно. Деактивацию так же легко отправить
через `PATCH`, хотя этот метод refresh не отзывает. Сеть здесь
проверяется моком `fetch`, без браузера. Форму запроса после этой задачи
выбирает стор, а не экран списка из [задачи 2](./02-admins-list.md).

## ⚠ Технические нюансы и ограничения

- `isActive` в query — строки `true` и `false`, см.
  [решения этапа](./README.md#решения-по-открытым-вопросам-этапа).
  В JSON тела `PATCH` то же поле — boolean. Строка `"false"` в теле не
  пройдёт `@IsBoolean`. Пропуск параметра из-за `if (isActive)` уберёт
  из запроса как раз фильтр неактивных. Состояние «все» — это отсутствие
  параметра. Пустой `isActive=` и пустая строка сюда не подходят: сервер
  не примет их как boolean и ответит `400`.
- `DELETE /admins/:id` отвечает `200` и телом сотрудника с
  `isActive: false`. Это не `204`. Метод деактивации читает тело.
  Пустой ответ на этом пути — сбой разбора, принимать его за успех
  нельзя.
- `PATCH /admins/:id/password` отвечает `204` без тела. Клиент этапа 0
  на пустом успехе возвращает `undefined`; метод стора не разбирает этот
  результат повторно. Тело запроса — только `{ newPassword }`.
  В пути — uuid сотрудника. Сегмент `me` метод не подставляет:
  `/admins/me/password` — другой контракт, им уже занята смена своего
  пароля.
- `403` и `409` возвращаются экрану как ошибка с `message`. Стор сессии
  они не очищают и `POST /auth/staff/refresh` не запускают. `401`
  по-прежнему обрабатывает перехватчик этапа 1. Второго обработчика в
  этом модуле нет.
- В ответе создания пароля нет. Стор не добавляет такое поле и не
  хранит пароль после отправки.
- В `src/stores/root-store.ts` появляется поле `admins` рядом с
  `session`. Файл HTTP-клиента и перехватчик `401` эта задача не меняет.
  Параллельно с задачей 2 её вести нельзя: экран вызывает методы ниже.

## Объём работы

- Стор MobX, один на приложение, поле корневого стора. Методы ходят
  через клиент этапа 0; access берётся из его геттера:
  - список: `GET /admins`, ответ — страница `{ items, total, page, limit }`;
  - создание: `POST /admins`, успех `201`;
  - правка: `PATCH /admins/:id`, в теле только переданные `role` и/или
    `isActive` (boolean);
  - деактивация: `DELETE /admins/:id`, успех `200` с телом;
  - сброс пароля: `PATCH /admins/:id/password`, успех `204`.
- Query списка собирается в этом модуле. Пустой `search`, невыбранные
  `role` и `isActive` в query не попадают. `page` и `limit` уходят в
  query числами, когда их передал вызывающий код.
- Тесты на моке `fetch`:
  - фильтр неактивных содержит ровно `isActive=false`, а не пустой
    параметр и не `isActive=true`;
  - состояние «все» не содержит `isActive`; пустой поиск не содержит
    `search`;
  - ответ `DELETE` читается как JSON и не считается пустым `204`;
  - сброс пароля шлёт `{ newPassword }` на путь с uuid; в теле нет
    `currentPassword`, в пути нет сегмента `me`;
  - при `403` и `409` вызов завершается ошибкой с `message` сервера,
    ключ refresh в переданном хранилище остаётся, второго `fetch` на
    `/auth/staff/refresh` нет.

## Критерии готовности

- Тесты из объёма работы проходят через `npm run test`.
- `npm run lint` проходит.
- В модуле стора есть пути `/admins` и нет пути `/admins/me/password`.
  Смена своего пароля из этого модуля не вызывается. Проверяется
  чтением модуля.
