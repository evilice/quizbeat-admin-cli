## Зачем

DoD этапа требует смену порядка и проверку, что в `noteIds` уходит
полный текущий набор. Отдельная задача не ломает тест формы из
задачи 3 и не смешивает его с удалением. ТЗ говорит «меняет порядок»,
не «перетаскивание» — достаточно кнопок «выше» / «ниже».

## Границы задачи

| Входит | Не входит |
|---|---|
| Действия смены порядка на списке (кнопки «выше» / «ниже» или эквивалент); после действия — `PATCH .../notes/order` с полным `noteIds` | Создание и правка — [задача 3](./03-note-form.md) |
| Обновление порядка на экране из ответа `200` или повторного `GET` | Удаление — [задача 5](./05-notes-delete.md) |
| Тест: в теле уходит полный текущий набор id в новом порядке; пустой массив не шлётся; путь содержит сегмент `order` | Обязательная DnD-библиотека; зависимость ради симметрии с картинками этапа 6 не добавлять |
| Показ `message` при `400` несовпадения набора | `imageIds` / картинки — [этап 6](../step-6/03-images-reorder.md) |

## ⚠ Технические нюансы и ограничения

- `noteIds` — **полная замена**, не diff. После перестановки в запрос
  должны попасть все id текущего списка ровно по одному разу, в новом
  порядке. Пустой список на сервер не уходит (`@ArrayMinSize(1)`); на
  пустом UI менять порядок не из чего.
- Несовпадение с серверным набором — `400` с текстом
  `NOTE_ID_SET_MISMATCH_MESSAGE`. Показать `message`, сессию не
  чистить. После чужого удаления/создания имеет смысл перечитать
  список перед повторной сменой порядка.
- Путь — `.../notes/order`, литеральный сегмент. Не подставлять UUID
  заметки вместо `order` и не слать тело на `PATCH .../notes/:noteId`.
  См. [README](./README.md#решения-по-открытым-вопросам-этапа).
- UI по умолчанию — кнопки «выше» / «ниже» (или аналог MUI). DnD не
  требуется. Если при реализации всё же поставят перетаскивание —
  DoD-тест смотрит на тело `noteIds`, не на API жеста; имя пакета в
  этой задаче не фиксируется.
- Общий файл — блок задачи 2. Вливать после 03, до 05 при конфликте.

## Объём работы

- На строке списка — действия, меняющие позицию (выше / ниже;
  крайние позиции корректно недоступны или no-op без сети).
- По действию — вызов стора с полным массивом id в новом порядке;
  успех → актуальный порядок на экране (`order` с 0).
- Отказ API — на блоке, без очистки сессии.
- Тесты (мок `fetch` / стора):
  - после имитации смены порядка в сети уходит `PATCH` на
    `.../notes/order` с телом `{ noteIds: [...] }`, длина и состав
    совпадают с текущим списком до запроса, порядок — новый;
  - пустой `noteIds` не отправляется;
  - URL содержит `/order`, а не uuid на месте сегмента `order`;
  - `400` с сообщением несовпадения набора показывает `message`.

## Критерии готовности

- Тесты из объёма работы проходят через `npm run test` — в том числе
  тест полного `noteIds` и пути с сегментом `order`.
- `npm run lint` проходит.
- Ручной ориентир: после смены порядка повторный `GET .../notes`
  совпадает с экраном; полный проход — у
  [приёмки](./06-step7-acceptance.md).
