## Зачем

Список, форма и удаление должны вызывать один модуль. Поле перевода у
тега называется `name`, у заметки — `text`; массив из двух локалей легко
отправить объектом или одним элементом. `DELETE /tags/:id` отвечает
пустым `204`, и разбор JSON на этом пути превращает успех в ошибку.
Сеть здесь проверяется моком `fetch`, без браузера. Форму запроса после
этой задачи выбирает стор, а не экран списка из
[задачи 2](./02-tags-list.md).

## ⚠ Технические нюансы и ограничения

- `translations` — массив ровно из двух элементов, у каждого `locale`
  (`ru` или `en`) и `name`. Объект вида `{ ru: '...', en: '...' }` и
  поле `text` сервер не примет: первое не массив, второе для
  валидатора пустое `name`. Дубль одной локали при двух элементах
  проходит `@ArrayMinSize(2)` и падает уже в сервисе с `400` и
  `message`
  `Translations must include exactly one entry per locale (ru, en), without duplicates`
  ([`assertCompleteTranslations`](../../../../quizbeat-srv/src/common/assert-complete-translations.ts)).
- `PATCH`, в котором передан `translations`, заменяет набор целиком.
  Метод стора кладёт в тело оба элемента, которые получил. Схлопнуть
  массив до изменённой локали нельзя: сервер тогда ответит `400`, а при
  обходе проверки стёр бы второй перевод
  ([`TagsService.update`](../../../../quizbeat-srv/src/tags/tags.service.ts)
  удаляет строки переводов и вставляет присланный набор).
- `DELETE /tags/:id` отвечает `204` без тела. Клиент этапа 0 на пустом
  успехе возвращает `undefined`; метод стора не разбирает этот результат
  повторно. Это другой контракт, чем `DELETE /admins/:id` (`200` с телом).
  Путь — uuid тега. Отдельного `GET /tags/:id` нет, метод его не
  заводит.
- Занятый `code` — `409` и `message` `Tag with this code already exists`
  ([`CODE_ALREADY_EXISTS_MESSAGE`](../../../../quizbeat-srv/src/tags/constants.ts)).
  Нет тега — `404`. Оба возвращаются экрану как ошибка с `message`. Стор
  сессии они не очищают и `POST /auth/staff/refresh` не запускают. `401`
  по-прежнему обрабатывает перехватчик этапа 1. Второго обработчика в
  этом модуле нет.
- В `src/stores/root-store.ts` появляется поле `tags` рядом с уже
  существующими полями. Файл HTTP-клиента и перехватчик `401` эта задача
  не меняет. Параллельно с задачей 2 её вести нельзя: экран вызывает
  методы ниже.

## Объём работы

- Стор MobX, один на приложение, поле корневого стора. Методы ходят
  через клиент этапа 0; access берётся из его геттера:
  - список: `GET /tags`, ответ — страница `{ items, total, page, limit }`;
  - создание: `POST /tags`, успех `201`, тело `{ code, translations }`;
  - правка: `PATCH /tags/:id`, успех `200`, тело с переданными `code` и
    `translations`;
  - удаление: `DELETE /tags/:id`, успех `204`.
- Query списка собирается в этом модуле. Пустой `search` и строка из
  одних пробелов в query не попадают. `page` и `limit` уходят в query
  числами, когда их передал вызывающий код.
- Тесты на моке `fetch`:
  - непустой `search` уходит одним query-параметром; пустой поиск и
    пробелы параметра `search` не содержат;
  - `POST` отправляет `translations` массивом из двух элементов с полями
    `locale` и `name`; в JSON нет поля `text` и нет объекта, ключи
    которого — локали;
  - `PATCH` на путь с uuid отправляет оба переданных перевода, а не один;
  - ответ `DELETE` с пустым телом и кодом `204` считается успехом и не
    читается как JSON;
  - при `404` и `409` вызов завершается ошибкой с `message` сервера,
    ключ refresh в переданном хранилище остаётся, второго `fetch` на
    `/auth/staff/refresh` нет.

## Критерии готовности

- Тесты из объёма работы проходят через `npm run test`.
- `npm run lint` проходит.
- В модуле стора есть пути `/tags` и нет пути `/tags/:id` как отдельного
  чтения одного тега. Проверяется чтением модуля.
