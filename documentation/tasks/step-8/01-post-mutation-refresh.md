# Задача 1 — Обновление блоков после мутаций

Этап: 8 — Сборка карточки композиции.
Зависимости: карточка уже открывается одним `GET .../full` —
[задача 4 этапа 4](../step-4/04-composition-card.md); сторы и UI мутаций —
[этап 5](../step-5/README.md), [этап 6](../step-6/README.md),
[этап 7](../step-7/README.md), правка композиции — та же
[задача 4 этапа 4](../step-4/04-composition-card.md).
Ссылка на ТЗ: [раздел «Этап 8»](../../03-technical-specification.md#этап-8--сборка-карточки-композиции)
(после мутации — актуальный блок; не смешивать устаревший `fileUrl`).
Правила по мутациям — таблица в
[README этапа](./README.md#обновление-после-мутаций).

## Зачем

Ответы мутаций неоднородны: одни отдают полный текущий набор блока,
другие — только новые элементы, одну сущность или пустой `204`. Если
каждый блок решит стык сам, легко подменить `images` массивом из двух
новых файлов и потерять третью или записать `PATCH` композиции поверх
всего экрана и обнулить `clips`. Одна задача на стык + общие тесты на
моке фиксируют таблицу README, не размазывая правило по четырём экранам.
Это единственная задача этапа 8: открытие карточки одним `GET .../full` и
первый рендер блоков из этого же ответа уже сделаны на этапах 4–7.

## Границы задачи

| Входит | Не входит |
|---|---|
| Проводка обновления экрана/стора после мутаций по [таблице README](./README.md#обновление-после-мутаций) | Новые поля форм, новый маршрут, смена multipart |
| Тесты на моке: частичный `POST .../images` не затирает уже показанные; `PATCH` композиции не обнуляет `clips` / `images` / `notes`; после `POST .../audio` прежний `originalAudioUrl` не остаётся | Переписывание опроса, DnD, формы заметок с нуля — только стык данных после успеха |
| Обновление протухших presigned (оригинал / картинка / `DONE`-отрезок) без переиспользования сохранённой строки | Приёмка на живом сервере — [задача 2](./02-step8-acceptance.md) |
| | Первая загрузка карточки и первый рендер блоков из `GET .../full` — уже сделаны [задачей 4 этапа 4](../step-4/04-composition-card.md) и блоками этапов 5–7 |

## ⚠ Технические нюансы и ограничения

- Полная таблица и обоснование «свой `GET` блока vs `GET /full`» — в
  [README](./README.md#обновление-после-мутаций). Кратко критичное:
  - `POST .../audio` → длительность из `201`, URL заново
    **`GET .../audio`**; старый `originalAudioUrl` сбросить;
  - `POST .../images` / `POST .../clips` → **не** подменять блок
    ответом; полный набор — `GET .../images` / опрос `GET .../clips`;
  - `PATCH .../images/order` и `PATCH .../notes/order` → можно
    заменить блок ответом (`list()`);
  - `POST` / `PATCH` одной заметки → не подменять массив одной
    заметкой; после `POST` — `GET .../notes`; после `PATCH` —
    заменить элемент с тем же `id`;
  - `DELETE` (`204`) → перечитать `GET` затронутого блока;
  - `PATCH /compositions/:id` → только поля композиции и `tags`.
- Не склеивать новый список отрезков/картинок с `fileUrl` /
  `originalAudioUrl` из первого `GET /full`: у каждого элемента URL
  должен быть из того ответа, которым заменили блок (или из явного
  обновления ссылки).
- Опрос при `PENDING` / `PROCESSING` по-прежнему заменяет `clips`
  целиком ответом `GET .../clips` — это уже этап 5; здесь проверить,
  что опрос не мержит со снимком из первого `GET /full`.
- Конфликт на файлах блоков 5–7 и карточки 4: эта задача только
  проводит правило обновления через уже существующий код, новых файлов
  не заводит.

## Объём работы

- После каждой мутации из таблицы README экран/стор обновляет
  затронутый блок выбранным способом (без «либо так, либо так»).
- Общий модуль или явные методы стора — на усмотрение, лишь бы не
  копировать расходящиеся правила в четырёх местах без теста.
- Тесты на моке (минимум):
  - на экране уже три картинки из `GET /full`; `POST .../images`
    возвращает два новых объекта → после обработки на экране не ровно
    эти два (третья не пропала); в сети есть `GET .../images` (или
    согласованный полный набор), которым блок заменён;
  - на экране есть `clips` из `GET /full`; успешный
    `PATCH /compositions/:id` с новым `title` → `title` обновлён,
    массив `clips` на экране не стал `undefined` / пустым из-за ответа
    `PATCH`;
  - после успешного `POST .../audio` прежний `originalAudioUrl` не
    используется для волны; в сети есть `GET .../audio`;
  - `POST .../clips` с массивом из одного нового отрезка **не**
    оставляет на экране только этот один, если раньше были другие:
    полный список приходит опросом / `GET .../clips`;
  - после `DELETE` картинки / заметки / отрезка удалённого `id` нет в
    соответствующем блоке (перечитан свой `GET`).

## Критерии готовности

- Тесты из объёма работы проходят через `npm run test`.
- `npm run lint` проходит.
- В коде нет пути, который присваивает блоку `images` / `clips` /
  `notes` тело частичного `POST` как полный набор. Проверяется тестами
  выше.
