# Задача 4 — Удаление тега

Этап: 3 — Справочник тегов.
Зависимости: [задача 2](./02-tags-list.md) (строка списка) и метод
удаления из [задачи 1](./01-tags-store.md).
Ссылка на ТЗ: [раздел «Этап 3»](../../03-technical-specification.md#этап-3--справочник-тегов)
(`DELETE /tags/:id` — жёсткое удаление, `204`, с подтверждением;
композиции теряют тег и сами не удаляются).
Карта: строка `DELETE /tags/:id` в
[тегах](../../02-staff-api.md#4-теги).
Сервис —
[`TagsService.remove`](../../../../quizbeat-srv/src/tags/tags.service.ts),
связь с композицией —
[`CompositionTag`](../../../../quizbeat-srv/src/compositions/composition-tag.entity.ts)
(`tagId` → `Tag.id`, `ON DELETE CASCADE`).

## Зачем

Удаление тега необратимо, и его легко оформить как деактивацию
сотрудника: та кнопка зовёт `DELETE` и оставляет строку в списке.
Здесь `204` убирает тег совсем, а каскад на сервере снимает связи с
композициями, не удаляя сами композиции. Подтверждение — единственное
место, где человек это видит до запроса: экрана композиций на этом
этапе ещё нет. Задача опирается на готовую строку из задачи 2: без кода
и названий в тексте нечего назвать.

## Границы задачи

| Входит | Не входит |
|---|---|
| Удаление строки через `DELETE /tags/:id` с подтверждением | Создание и правка — [задача 3](./03-tag-form.md) |
| Текст подтверждения: безвозвратно, композиции теряют связь и остаются, восстановления нет | Проверка каскада на живой композиции. Карточки композиций ещё нет, это [этап 4](../../03-technical-specification.md#этап-4--композиции) |
| После `204` список перечитывается, строки больше нет | Возврат удалённого тега. Такого действия на сервере нет |

## ⚠ Технические нюансы и ограничения

- Удаление — `DELETE`, успех `204` без тела. Метод стора из задачи 1
  уже считает пустой ответ успехом. Повторно читать тело в обработчике
  кнопки нельзя: пустой `204` так превращается в ошибку разбора, и
  список не обновляется, хотя тег на сервере уже удалён.
- Текст подтверждения по-русски говорит три вещи: тег удаляется
  безвозвратно; композиции, на которых он был, теряют с ним связь и сами
  не удаляются; вернуть тег нельзя. Формулировки «деактивировать» нет:
  после успеха строки в списке не остаётся. Отмена подтверждения не
  вызывает `fetch`. См.
  [решения этапа](./README.md#решения-по-открытым-вопросам-этапа).
- В подтверждении видны код и оба названия удаляемой строки, чтобы
  соседние теги не путались. Названия берутся по `locale`.
- `404` (тег уже удалён) показывает `message` сервера и перечитывает
  список. `409` на этом пути сервер не отвечает: занятый код относится
  к созданию и правке.
- После `204` список перечитывается с текущим поиском и страницей.
  Строка до ответа сервера из таблицы не исчезает. Ответ удаления в
  таблицу не подмешивается: тела у него нет.
- Экран списка общий с задачей 3. Эта задача добавляет на строку
  удаление. При конфликте слияния она идёт после задачи 3, см.
  [README](./README.md#почему-такой-порядок).

## Объём работы

- На строке действие «Удалить» открывает подтверждение с кодом и обоими
  названиями. Подписи русские. В тексте есть три последствия из нюанса
  выше.
- Отмена закрывает подтверждение и не вызывает `fetch`. Согласие
  вызывает `DELETE` с id строки.
- При успехе список запрашивается заново с текущим поиском и страницей,
  подтверждение закрыто. При `404` на экране виден `message`, список
  запрашивается заново.
- Тесты:
  - отмена не вызывает `fetch`, строка остаётся;
  - согласие шлёт `DELETE` на путь с uuid этой строки и не шлёт тело;
  - пустой `204` убирает подтверждение и вызывает повторное чтение
    списка;
  - до ответа сервера строка в таблице на месте;
  - `404` показывает `message` и запрашивает список заново.

## Критерии готовности

- Тесты из объёма работы проходят через `npm run test`.
- `npm run lint` и `npm run build` проходят.
- В обработчике удаления нет чтения тела ответа и нет `PATCH` с признаком
  активности. Проверяется чтением обработчика.
