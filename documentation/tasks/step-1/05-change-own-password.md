Этап: 1 — Сессия сотрудника.

Контроллер —

## Зачем

Смена своего пароля доступна и `ADMIN`, и `SUPER_ADMIN` и не ждёт
списка сотрудников. Ей нужно уже вошедшее приложение из задачи 3 и
способ не принять опечатку текущего пароля за смерть сессии — этот
способ задача 2 оставила как разборщик, без него форма либо выкинет
человека на логин, либо заведёт второй перехватчик. Чужой сброс пароля
сюда не кладётся: он про другой путь и другую роль.

## Границы задачи

| Входит | Не входит |
|---|---|
| Форма текущего и нового пароля, `PATCH /admins/me/password`, ссылка на неё из шапки для любой роли | `PATCH /admins/:id/password` и экран чужого сотрудника — [этап 2](../../03-technical-specification.md#этап-2--сотрудники) |
| Короткий новый пароль не уходит на сервер | Пункт «Сотрудники» — [задача 4](./04-role-menu.md). Ссылка на эту форму живёт в шапке рядом с выходом, не внутри пункта сотрудников |
| После `204` — забыть refresh и оставить access текущей вкладки | Новый логин сразу после смены и выдача другой пары токенов. Сервер пару здесь не отдаёт |

## ⚠ Технические нюансы и ограничения

- Путь литеральный: `/admins/me/password`. Подставлять id из стора вместо
  `me` нельзя. На сервере `me/password` объявлен раньше `:id/password`;
  клиент, который шлёт uuid на свой же пароль, попадёт в сброс чужого
  пароля. У `ADMIN` это `403`, у супер-админа — смена «чужого» пароля
  без `currentPassword`, то есть другой контракт.
- Неверный текущий пароль — `401` и `message`
  `Current password is incorrect`. Access при этом валиден, refresh
  сервер не отзывает. Запрос передаёт разборщик задачи 2, который
  узнаёт эту строку и не даёт перехватчику ротировать сессию. Без
  разборщика цепочка такая: первый `401` → refresh → повтор PATCH с тем
  же неверным текущим → второй `401` → выход из сессии из-за опечатки.
  Протухший access на этом же вызове разборщик не перехватывает: строка
  гарда другая (`Invalid or missing access token`), срабатывает обычный
  один refresh и повтор.
- Успех — `204` без тела и без новой пары. Сразу после него стор забывает
  только refresh (метод задачи 1). Вызвать восстановление или refresh
  «чтобы обновить сессию» нельзя: токен уже отозван, ответ будет `401`,
  и задача 2 выкинет на логин при ещё живом access. Текущая вкладка
  остаётся в оболочке до конца TTL access. Перезагрузка открывает логин,
  потому что refresh в хранилище нет.
- Новый пароль короче 8 символов на сервер не отправляется. Порог — 8,
  как `MIN_PASSWORD_LENGTH`, не свой набор правил (цифры, разный регистр
  и т.п.). Пустой текущий тоже не отправляется. Если сервер всё же
  ответил `400` и `message` массивом, форма показывает весь список через
  уже существующий разбор ошибки.
- Ответ и подписи полей рисуются текстом React, без
  `dangerouslySetInnerHTML`.
- Шапка и таблица маршрутов общие с задачей 4. Эта задача добавляет
  ссылку «Сменить пароль» и свой маршрут. Пункт «Сотрудники» не
  двигает. При конфликте слияния задача 4 вливается раньше, см.
  [README](./README.md#почему-такой-порядок).

## Объём работы

- Маршрут смены пароля внутри уже вошедшей оболочки, ссылка в шапке
  видна и `ADMIN`, и `SUPER_ADMIN`. Без сессии маршрут ведёт на логин,
  как остальные закрытые пути задачи 3.
- Поля «текущий пароль» и «новый пароль», отправка JSON
  `{ currentPassword, newPassword }` на `/admins/me/password` клиентом
  этапа 0 с access из стора и с разборщиком `401` для строки
  `Current password is incorrect`.
- Клиентская проверка до запроса: новый пароль короче 8 — русское
  сообщение на форме, `fetch` не вызывается.
- `204`: русское подтверждение, что пароль изменён, поля очищены, refresh
  забыт, оболочка на месте. `401` с текстом про текущий пароль: это
  сообщение на форме, сессия и ключ refresh целы. Прочий отказ
  (`400` с массивом, сеть) показывает разобранное сообщение тем же
  способом, что логин.
- Тесты:
  - новый пароль из 7 символов не вызывает `fetch`;
  - успешный `204` вызывает метод «забыть refresh», access в сторе
    остаётся, форма показывает подтверждение;
  - ответ `401` с `Current password is incorrect` показывает эту строку,
    не шлёт `POST /auth/staff/refresh` и не очищает access;
  - ссылка на форму есть в шапке при роли `ADMIN`.

## Критерии готовности

- Тесты из объёма работы проходят через `npm run test`.
- `npm run lint` и `npm run build` проходят.
- Поиск по модулю формы находит путь `me/password` и не находит
  подстановку id сотрудника в URL смены своего пароля.
- В форме нет второго разбора тела ошибки: сообщения приходят из модуля
  этапа 0. Проверяется чтением импортов формы.
