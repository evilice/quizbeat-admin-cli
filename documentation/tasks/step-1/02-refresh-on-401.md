## Зачем

DoD этапа требует тест: на пачку параллельных `401` уходит один refresh,
и старый refresh после успеха больше не отправляется. Это свойство
клиента, а не экрана. Пока его нет, логин в
[задаче 3](./03-login-logout.md) легко заведёт свой `fetch` мимо ротации,
и два места будут по-разному переживать протухший access. Здесь
появляется единственный модуль вызовов сессии и единственная доработка
клиента этапа 0.

## Границы задачи

| Входит | Не входит |
|---|---|
| `POST /auth/staff/login`, `/auth/staff/refresh`, `/auth/staff/logout` через клиент этапа 0 | Разметка экрана логина, редиректы, момент вызова восстановления при старте — [задача 3](./03-login-logout.md). Метод восстановления стор отдаёт, маршрутизатор его не вызывает |
| Один общий refresh на пачку параллельных `401`, повтор исходных запросов новой парой | Смена своего пароля `PATCH /admins/me/password` — [задача 5](./05-change-own-password.md). Здесь только способ сказать перехватчику «этот `401` не про токен» |
| Запись пары в стор задачи 1 и стирание сессии, когда refresh отвергнут | Пункт меню и разбор роли в вёрстке — [задача 4](./04-role-menu.md) |

## ⚠ Технические нюансы и ограничения

- Логин, refresh и logout через перехватчик `401` не идут. Неверный пароль
  — тоже `401` (`Invalid credentials`). Если в хранилище ещё лежит
  прежний refresh, перехватчик воспримет его как протухший access,
  ротирует чужую или старую сессию и спрячет сообщение сервера. У этих
  трёх вызовов заголовок `Authorization` не ставится: на контроллере
  гарда нет.
- `POST /auth/staff/refresh` изнутри обработки `401` не должен снова
  попасть в ту же обработку. Иначе один негодный refresh зацикливает
  клиент. Отдельный внутренний вызов, без повторной попытки.
- Повтор исходного запроса читает геттер access заново. Заголовок,
  снятый с первого `fetch` и подставленный второй раз, несёт уже
  отвергнутый токен: сервер снова отвечает `401`, и правило «повторный
  `401` — выход» выкинет живую сессию сразу после успешной ротации.
  Тело повтора берётся из того, что клиент уже сериализовал для первой
  попытки. `response.json()` первого ответа тело запроса не трогает, но
  поток `BodyInit`, который нельзя прочитать дважды, для повтора не
  годится. На этом этапе тела — JSON-строки; контракт повтора их
  сохраняет.
- Параллельные `401` делят один promise. Два независимых `refresh` с
  одним и тем же токеном: первый успевает отозвать его в БД, второй
  получает `401`, и клиент, услышав этот `401`, сотрёт как раз
  новую пару. Тот же promise использует восстановление сессии, когда
  его позовёт задача 3. Второй механизм «на время старта страницы» не
  заводится.
- Успешный refresh пишет новую пару через метод задачи 1 без email,
  чтобы не затереть почту. В следующий refresh уходит уже новый токен.
  Старый после успеха ни один вызов больше не шлёт — сервер его отозвал,
  повтор был бы `401`.
- `401` на самом refresh стирает access и refresh и оставляет email
  (метод задачи 1). `429` и сетевой отказ refresh токены не стирают и
  второй refresh сами не запускают: лимит (20 за 60 с) отвечает гард до
  ротации, обрыв — это не HTTP-ошибка клиента этапа 0. Исходные запросы
  при этом завершаются своей ошибкой. Решение общее для этапа, см.
  [README](./README.md#решения-по-открытым-вопросам-этапа).
- Вызов может передать разборщик уже разобранной ошибки `401`. По
  умолчанию разборщика нет, и любой `401` защищённого вызова идёт в
  refresh. Разборщик, который сказал «это не токен», возвращает ошибку
  вызывающему коду: без refresh и без очистки сессии. Задача 5 передаст
  его для `Current password is incorrect` и этот файл не откроет.
- Logout шлёт текущий refresh и при любом исходе запроса (204, сеть,
  401) локально чистит сессию целиком, включая email. Ответ `204` без
  тела клиент этапа 0 уже умеет. Пустой refresh на сервер не отправляется:
  DTO требует непустую строку, ушёл бы `400`. Тогда чистится только
  локальное состояние.
- Тест этапа 0 «при `401` уходит ровно один `fetch`» написан для клиента
  без сессии. Его не помечают `.skip`. Он остаётся верным для вызова,
  который в перехватчик не входит (логин). Для защищённого вызова
  ожидаемое число запросов другое — его фиксируют тесты ниже.
- Файл разбора ошибки и `src/api/api-base-url.ts` не меняются. Меняется
  клиент, который на `401` защищённого вызова теперь делает второй шаг.

## Объём работы

- Методы стора сессии: логин (email и пароль → пара в сторе),
  восстановление (один refresh текущим токеном из хранилища), выход.
  Восстановление при отсутствии refresh ничего не шлёт и завершается
  сразу. Логин при `401` и при `429` стор не заполняет и запрос не
  повторяет.
- Доработка клиента: защищённый вызов с `401` один раз запускает общий
  refresh и повторяет себя с новым access. Повторный `401` после этого
  очищает сессию так же, как `401` самого refresh. Незащищённые три
  вызова сессии этот путь не включают.
- Тесты на моке `fetch`, без сервера:
  - логин `200` пишет пару; логин `401` и логин `429` — ровно один
    `fetch`, стор пустой;
  - несколько защищённых вызовов одновременно получают `401`: ровно один
    `POST /auth/staff/refresh` со старым токеном, каждый исходный запрос
    повторён уже с новым access, в хранилище лежит новый refresh;
  - следом ещё один refresh уходит с новым токеном, старого в теле нет;
  - refresh ответил `401`: второго refresh нет, access и refresh стёрты,
    исходные запросы не зациклены;
  - refresh ответил `429` или мок `fetch` отверг его сетью: ключ refresh
  на месте, третьего запроса нет;
  - разборщик сказал «не токен»: refresh не вызывается, сессия на месте,
  вызывающий код получает эту ошибку;
  - logout при `204` и при сетевом отказе оба очищают хранилище; logout
  без сохранённого refresh не делает `fetch`.

## Критерии готовности

- `npm run test` содержит случаи пачки параллельных `401`, однократного
  refresh и запрета повторно отправить старый токен после успеха. Это
  проверка DoD этапа про ротацию; браузер её не заменяет.
- Тест логина на `429`: один запрос, без паузы и без второго `fetch`.
- `npm run lint` и `npm run build` проходят.
- Поиск по `src/` находит путь `/auth/staff/refresh` в одном модуле
  вызова, не в экранах и не второй копией внутри компонента.
