# Задача 1 — Модель сессии: access, refresh и email

Этап: 1 — Сессия сотрудника.
Зависимости: [HTTP-клиент этапа 0](../step-0/02-http-client.md) (геттер
access уже предусмотрен, клиент сам токен не хранит) и
[корневой стор](../step-0/03-app-shell.md) (`src/stores/root-store.ts`).
Ссылка на ТЗ: [раздел «Этап 1»](../../03-technical-specification.md#этап-1--сессия-сотрудника)
(роль и id из access, почта рядом с refresh) и
[раздел 2](../../03-technical-specification.md#2-общие-технические-требования)
(access в памяти, refresh в `localStorage`).
Карта: [сессия](../../02-staff-api.md#2-сессия), payload —
[`StaffAccessTokenPayload`](../../../../quizbeat-srv/src/staff-auth/types/staff-user.type.ts).
Поля токена, уже перечисленные в карте, здесь не повторяются.

## Зачем

Ротация и экраны должны писать в одно и то же место. Если форму логина
и перехватчик `401` завести раньше модели, каждая положит refresh в свой
ключ и DoD «после перезагрузки сессия жива» разъедется на две
реализации. Сеть в эту задачу не входит: её нечем честно проверить без
мока `fetch`, а мок refresh — уже [задача 2](./02-refresh-on-401.md).

## Границы задачи

| Входит | Не входит |
|---|---|
| Разбор payload access без проверки подписи: `sub`, `role`, `type` | `POST /auth/staff/login`, refresh, logout и повтор запроса после `401` — [задача 2](./02-refresh-on-401.md) |
| Access в памяти, refresh и email в хранилище, поле `session` у корневого стора | Экран логина, шапка, восстановление при старте страницы — [задача 3](./03-login-logout.md) |
| Состояния «сессия есть», «refresh забыт, access ещё в памяти», «токены сброшены, email остался» | Смена пароля, которая переводит стор во второе состояние, — [задача 5](./05-change-own-password.md). Здесь только метод, которым она это сделает |
| | Пункт меню по роли — [задача 4](./04-role-menu.md). Стор отдаёт роль, меню не рисует |

## ⚠ Технические нюансы и ограничения

- Подпись не проверяется, секрет сервера в клиент не попадает. Отдельный
  пакет для JWT не ставится. Берётся средний сегмент (их три, делятся
  точкой). Алфавит — base64url: `-` и `_` надо заменить на `+` и `/` до
  `atob`, иначе часть настоящих токенов молча не разберётся. Паддинг `=`
  до длины, кратной 4, обязателен. Результат `atob` — бинарная строка;
  email в этом токене нет, но `JSON.parse` всё равно кормить через
  `TextDecoder` (UTF-8), а не через побайтовое приведение, которое
  сломается на первом же не-ASCII, если состав payload когда-нибудь
  расширят.
- `type !== 'staff'` — чужой контур (player), даже если `sub` и `role`
  на вид похожи на наши. Такой токен не записывается. Роль, отличная от
  `ADMIN` и `SUPER_ADMIN`, тоже не сессия: меню задачи 4 сравнивает роль
  на строгое равенство, а «какая-то строка» не должна становиться
  супер-админом.
- Email в access нет, в refresh нет. Метод установки пары принимает
  email отдельно. Повторный вызов без email (так делает успешный refresh
  в задаче 2) сохраняет уже записанную почту, а не затирает её пустым.
- Хранилище передаётся аргументом. Тест, который читает настоящий
  `localStorage` окна, цепляет ключи соседнего прогона и локальный мусор
  разработчика — та же ловушка, что с `.env` в
  [задаче 1 этапа 0](../step-0/01-project-scaffold.md). В приложении
  аргумент — `window.localStorage`.
- Ключи фиксируются здесь и дальше не переименовываются:
  `quizbeat.staff.refreshToken`, `quizbeat.staff.email`. Access в
  хранилище не пишется ни под каким ключом.
- `src/stores/root-store.ts` заведён на этапе 0 без полей. Здесь у него
  появляется `session`. Файл HTTP-клиента эта задача не меняет: геттер
  токена задача 2 соединит со стором сама. Параллелить с задачей 2
  нельзя — она опирается на методы ниже.

## Объём работы

- Чистая функция разбора access. На выходе либо `{ id, role }`, где
  `role` — `'ADMIN' | 'SUPER_ADMIN'`, либо отказ. Отказ на обрезке
  строки, не-JSON, не том `type`, пустом `sub`, чужой роли. Подпись
  (третий сегмент) функцией не читается.
- Стор сессии MobX, один на приложение, поле корневого стора:
  - установить пару access + refresh и необязательный email;
  - забыть только refresh (access и email остаются) — это состояние
    после успешной смены своего пароля, см.
    [решения этапа](./README.md#решения-по-открытым-вопросам-этапа);
  - сбросить access и refresh, email оставить — отказ refresh в задаче 2;
  - очистить всё, включая email — выход в задаче 3;
  - прочитать access для геттера HTTP-клиента, id, роль и email для
    оболочки.
  Access живёт в поле стора. Refresh и email пишутся в переданное
  хранилище в том же действии, что и смена памяти, чтобы перезагрузка
  между двумя присваиваниями не видела пару наполовину.
- Стор при создании читает refresh и email из хранилища, но сам
  `POST /auth/staff/refresh` не вызывает и access из этого чтения не
  выдумывает. Пока задача 3 не восстановила сессию, id и роль — пустые,
  даже если refresh в хранилище уже лежит.
- Тесты функции разбора и стора, без `fetch` и без jsdom-экрана:
  валидный payload `staff` с каждой из двух ролей; player-`type`; битая
  строка; установка пары пишет refresh и email и не пишет access;
  повторная установка пары без email оставляет прежний email и меняет
  refresh; «забыть refresh» оставляет access в памяти и удаляет ключ
  refresh; полная очистка удаляет оба ключа.

## Критерии готовности

- Тесты из объёма работы проходят через `npm run test`. В хранилище
  теста после установки пары нет строки access-токена.
- `npm run lint` и `npm run build` проходят: у корневого стора есть
  `session`, разбор токена типизирован вместе с приложением.
- Поиск по `src/` не находит `/auth/staff` в файлах этой задачи.
  Проверяется поиском. Вызовы появятся в
  [задаче 2](./02-refresh-on-401.md).
