# Правила оформления задач разработки

Адаптация [соглашения бэкенда](../../../quizbeat-srv/documentation/tasks/task-writing-guidelines.md)
под этот репозиторий. Структура файлов и обязательные секции те же, чтобы
задачи обоих репозиториев читались одинаково. Примеры ловушек — про
веб-клиент и контракт `quizbeat-srv`, не про NestJS.

Соглашение для документов в `documentation/tasks/step-N/`. Применяется при
декомпозиции любого этапа ТЗ на задачи для разработки.

## 1. Структура директории

- Один этап ТЗ → одна директория `documentation/tasks/step-N/`, где `N` —
  номер этапа **как в ТЗ клиента** (Этап 0 → `step-0`, Этап 1 → `step-1`),
  без сдвига нумерации. Номера этапов — собственные: это порядок поставки
  экранов клиента, не номера этапов `quizbeat-srv`. Сессия — этап 1,
  сотрудники — этап 2, контент начинается с тегов на этапе 3.
- Имя файла задачи начинается с порядкового номера в порядке выполнения:
  `01-api-client.md`, `02-app-shell.md` и т.д. Порядок номеров =
  топологический порядок графа зависимостей, а не порядок появления пункта
  в тексте ТЗ.
- В каждой директории — файл `README.md`: таблица задач с колонкой
  «Зависит от» + mermaid-граф зависимостей + короткое обоснование порядка
  (почему что от чего зависит, что можно вести параллельно) + открытые
  вопросы этапа, которые не привязаны к одной конкретной задаче.
  **Открытые вопросы этапа фиксируются только там** — не в этом документе
  и не разбросаны по отдельным задачам, если вопрос затрагивает несколько
  из них сразу.

## 2. Обязательные секции файла задачи

Каждый файл `NN-slug.md` содержит секции в этом порядке:

1. **Заголовок и метаданные** — `# Задача N — <название>`, затем: этап,
   зависимости (со ссылками на файлы задач, не просто номера), ссылка на
   конкретный пункт/раздел ТЗ клиента (якорь, не просто «см. ТЗ»). Если
   задача ходит в API — ссылка на раздел
   [02-staff-api.md](../02-staff-api.md) и на контроллер или DTO в
   `quizbeat-srv`. Поля, которые уже есть в карте, внутри задачи не
   пересказываются.
2. **Зачем** — 2–4 предложения: почему задача нужна именно в этом месте
   графа зависимостей и именно в этом объёме. Не пересказ ТЗ, а
   обоснование решения о декомпозиции.
3. **Границы задачи** — двухколоночный список **Входит / Не входит**.
   Явно называть, в какую другую задачу/этап уезжает смежная
   функциональность, а не просто «остальное потом».
4. **Технические нюансы и ограничения** (⚠) — только специфичные для этого
   стека и для контракта сервера ловушки, не общие советы. Критерий
   включения пункта: «разработчик наткнётся на это на практике и потеряет
   время, если не предупредить заранее». Примеры такого уровня:
   - Переменные окружения Vite попадают в клиентский бандл только с
     префиксом `VITE_`. Имя без префикса молча остаётся `undefined`.
   - Dev-сервер слушает порт `5173`: на это значение уже выставлен
     `CORS_ORIGIN_ADMIN` бэкенда. Смена порта без правки env сервера
     выглядит как «API не отвечает», хотя падает CORS.
   - Access-токен staff содержит `sub`, `role` и `type: 'staff'`, но не
     email. Почту для шапки экрана нельзя прочитать из JWT.
   - `POST /auth/staff/refresh` ротирует refresh: повторно отправить
     предыдущий токен нельзя, сервер его уже отозвал.
   - `fileUrl` отрезка отсутствует в JSON, пока статус не `DONE` — это не
     `null`. Ссылка на оригинал и на картинку — presigned, TTL по умолчанию
     3600 секунд; класть её в стор как постоянный адрес нельзя.
   - `GET /compositions?tagIds=` — одна строка через запятую, не
     повторяющийся query-параметр. `GET /admins?isActive=` — строки
     `true` / `false`.
   - Multipart: исходный трек — поле `file`, картинки — поле `files`
     (до 10 файлов). Путать имена — `400`, файл до сервера не доходит.
   - Любой момент, где две задачи правят один и тот же файл (корневой
     роутер, HTTP-клиент, каркас стора сессии) — фиксировать ожидаемый
     порядок правок или предупреждать о конфликте.
   Если для задачи такой специфики нет — секция короткая или отсутствует
   с пометкой «нет» (не заполнять её общими фразами ради заполнения).
5. **Объём работы** — конкретные пункты реализации. Списки переменных
   окружения — таблицей (`имя | тип | обязательна | дефолт | назначение`),
   не прозой.
6. **Критерии готовности** — только проверяемые утверждения. Каждый пункт
   должен указывать **как** проверяется (тест / ручной проход в браузере /
   сверка с ответом сервера), а не только **что** должно быть верно.
   Формулировка «экран написан» — недостаточна.

## 3. Сквозные правила читаемости

- Заголовки секций одинаковы дословно во всех файлах этапа — так документы
  сканируются взглядом по одной и той же структуре.
- Ссылки на ТЗ, на другие задачи и на код сервера — всегда markdown-ссылки
  на конкретный якорь/файл, не текстовые упоминания вида «см. этап 1».
- Открытый вопрос, влияющий на решение внутри задачи, но не блокирующий её
  старт, — помечается явно (например, блок «Открытый вопрос») с
  предложенным дефолтным решением, а не оставляется как молчаливая
  неопределённость.
- Нюанс, актуальный для нескольких задач сразу, дублируется короткой
  перекрёстной ссылкой в каждой из них — не предполагается, что
  разработчик второй задачи прочитает первую целиком.
